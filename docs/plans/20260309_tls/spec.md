# MiaRec TLS Deployment Enhancements — Specification

## 1. Context & Goals (User/Business Perspective)
- **Problem**: Root playbooks (`prepare-hosts.yml`, `setup-miarec.yml`) cannot currently toggle TLS for PostgreSQL, PGBouncer, or Redis even though role submodules already support TLS. This gap prevents security-conscious customers from adopting MiaRec via the top-level automation.
- **Primary users**: Infra/SRE operators running MiaRec in regulated environments, security/compliance reviewers who mandate encrypted transport, and CI maintainers who must validate TLS installs.
- **Goals**:
  - Provide service-level TLS booleans (e.g., `postgresql_tls`, `pgbouncer_client_tls`, `redis_tls`) defaulting to `false`, each with associated certificate path variables.
  - Ship a repository Makefile that can generate self-signed CA/server/client bundles for each service when cert paths are omitted, mirroring `roles/miarecweb/molecule/tls/tasks/certificates.yml`.
  - Add a Molecule TLS scenario covering the full distro matrix in CI so TLS installations remain tested.
  - Plan for MiaRec Recorder TLS consumption; implement once the recorder role exposes TLS support (targeted by project completion).

## 2. Non-Goals / Out of Scope
- Managing long-lived production PKI lifecycles or integrating with LetsEncrypt/ACME (beyond existing role behavior).
- Introducing a global "enable TLS everywhere" toggle; per-service control is required for mixed deployments.
- Refactoring unrelated roles (Apache, LetsEncrypt, etc.) except where they must consume TLS-enabled services.
- Adding TLS to ancillary services (e.g., HAProxy, Sentinel) unless explicitly required.

## 3. Definitions / Glossary
- **Service TLS toggles**: Boolean variables such as `postgresql_tls`, `pgbouncer_client_tls`, `pgbouncer_server_tls`, `redis_tls` that independently enable TLS per component.
- **Self-signed chain**: CA + server + client certificates generated by the new Makefile when operators do not supply file paths; intended for development, Molecule, or initial bootstrap only.
- **TLS Molecule scenario**: A new top-level Molecule scenario (likely `tls`) that provisions TLS-enabled infra, reusing role-specific TLS logic and validated via Testinfra; executed across all supported distros in CI.

## 4. Functional Requirements

### 4.1 User stories
- As an infra operator, I can toggle `postgresql_tls: true` to install PostgreSQL with TLS, supplying cert paths or using Makefile-generated artifacts, so DIA connections are encrypted.
- As an operator, I can independently enable TLS for PGBouncer (client-facing, server-facing, or both) and Redis without impacting other services.
- As a developer/tester, when cert paths are unset, I can run `make tls-certs` (or service-specific targets) to create CA/server/client bundles aligned with defaults used by the playbooks and roles.
- As a CI maintainer, I can run `uv run molecule test -s tls` per distro matrix to ensure TLS installs stay green.

### 4.2 Use cases (happy path + key variants)
- **UC1 – Plain install**: All toggles remain false; behavior matches current baseline.
- **UC2 – PostgreSQL TLS only**: `postgresql_tls: true` configures TLS in `postgresql.conf` + `pg_hba.conf`, optionally requiring client certs; MiaRec web already consumes its TLS vars.
- **UC3 – Full stack TLS**: All toggles true, Makefile generates certs, MiaRec web consumes them now, and MiaRec recorder consumes them once the role supports TLS (documented deliverable).
- **UC4 – PGBouncer partial TLS**: PGBouncer terminates TLS on client side (`pgbouncer_client_tls: true`) but talks plaintext to PostgreSQL (`pgbouncer_server_tls: false`); playbooks must support this mix.

### 4.3 Edge cases & failure modes
- Missing cert paths while TLS toggles are true should fail fast with actionable errors unless the operator has explicitly invoked the helper Makefile (e.g., mention `make tls-certs-redis`).
- Mixed TLS states (Redis TLS on, PostgreSQL off) must not leak TLS config into other services.
- Recorder TLS support is pending; spec must document how it will hook into shared cert assets to avoid divergence between web/recorder.
- Ensure repeatable runs do not overwrite user-provided certs (idempotency).

## 5. Non-Functional Requirements
- **Security**: Favor TLS 1.2+ protocols and secure cipher suites already enforced by roles; apply least-privilege permissions (e.g., `0600` for keys). When Makefile generates certificates, note that they are non-production artifacts with ~365-day validity.
- **Performance**: Document expected CPU overhead for TLS; clarifies why toggles remain opt-in.
- **Reliability**: Makefile and playbooks must be idempotent and safe to re-run; they should skip regenerating certs if files already exist unless explicitly forced.
- **Observability/Testing**: Extend Molecule/Testinfra to confirm TLS ports listen, plaintext traffic fails, and TLS clients succeed (mirroring existing role-level TLS tests).
- **CI runtime**: Accept increased CI time due to full-matrix TLS scenario; surface gating in the spec so stakeholders approve.

## 6. UX / API Contracts (as applicable)
- **Inventory variables**: Document per-service booleans, cert/key/CA paths, Redis TLS auth (`redis_tls_auth_clients`), PostgreSQL/PGBouncer `sslmode` defaults, and how recorder vars will align once available.
- **Makefile UX**: Provide clear targets (e.g., `make tls-certs-postgresql`, `tls-certs-pgbouncer`, `tls-certs-redis`, `tls-certs-all`) that emit artifacts into predictable directories (e.g., `certs/postgresql/…`). Output should instruct operators to copy files securely to hosts when used outside Molecule.
- **Error handling**: When a required cert is missing, playbooks should fail with next-step hints (“Set `redis_tls_cert` or generate via `make tls-certs-redis`”).
- **Recorder onboarding**: Once TLS lands in the recorder role, expose variables mirroring MiaRec web semantics so the same inventory values apply across applications.

## 7. Data & State
- **Certificate locations**: Use canonical server-side paths (`/etc/postgresql/tls`, `/etc/pgbouncer/tls`, `/etc/redis/tls`) already expected by roles; Makefile should output matching filenames to reduce overrides.
- **Inventory state**: Capture booleans, cert paths, `sslmode` preferences, and (eventually) recorder TLS vars in `vars/db.yml`, `vars/web.yml`, or `vars/custom.yml`.
- **Molecule assets**: TLS scenario should generate certs inside containers (mirroring `roles/miarecweb/molecule/tls/tasks/...`), ensure cleanup between runs, and reuse the Makefile logic when possible to avoid duplication.

## 8. Acceptance Criteria (Top-level)
- Service-level TLS variables exist with documented defaults (`false`) and are consumed by root playbooks without breaking existing behavior.
- Makefile target(s) create self-signed CA/server/client certificates for PostgreSQL, PGBouncer (client + server), and Redis, matching expected permissions and file names.
- TLS-enabled deployments succeed for each service independently and collectively; plaintext deployments remain unaffected.
- MiaRec recorder TLS support is delivered before closing the project (can be the final implementation step once its role code is ready).
- Molecule gains a TLS scenario that executes across all supported distros in CI, validating TLS success and plaintext rejection.
- Spec references and links (idea.md, role TLS docs, etc.) are captured in the References section for traceability.

## 9. Open Questions
- **Recorder TLS timeline/owner**: Pending upstream work to expose TLS vars in the recorder role. Action: assign owner and track issue; implementation is required before project completion.
- **Future services**: Determine whether other services (e.g., Redis Sentinel, HAProxy, MiaRec Screen) will require TLS in upcoming phases; currently out of scope but should be reevaluated later.

## 10. Assumptions
- Operators will provide production-ready certificates; Makefile-generated assets are for development, Molecule, or bootstrap only.
- Recorder role TLS implementation will mirror MiaRec web variable names and defaults, allowing shared certs and toggles.
- CI resources can absorb longer runtime from full-matrix TLS tests.
- Submodule roles remain the source of truth for TLS configuration details; root playbooks primarily orchestrate toggles and variable wiring.
